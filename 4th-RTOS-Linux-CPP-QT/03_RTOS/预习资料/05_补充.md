# 1. 软件定时器

>软件定时器是FreeRTOS中基于系统时钟节拍实现的一个依赖于软件逻辑的定时器.  它允许任务在**设定时间到期后执行回调函数**.
>
>```C
>// 于TIM定时器不同, TIM定时器是基于片上外设这个硬件外设实现的定时器. 
>// 而在FreeRTOS中软件定时器, 不直接依赖于片上外设, 而是靠系统时钟节拍计时.
>```
>
>- 要使用软件定时器, 必须配置configUSE_TIMERS为1
>- 在调度器开启的时候, 如果我们启用了软件定时器, 那么调度器会自动创建一个**软件定时器服务任务**
>
>```C
>(tasks.c  3665)
>void vTaskStartScheduler( void )
>{
>    // ...
>    (3681)
>    #if ( configUSE_TIMERS == 1 )
>    {
>        if( xReturn == pdPASS )
>        {
>            xReturn = xTimerCreateTimerTask();
>        }
>        else
>        {
>            mtCOVERAGE_TEST_MARKER();
>        }
>    }
>    #endif
>    // ...
>}
>```
>
>- 定时器的本质是设置定时器, 定义**触发时间**和**回调函数**, 当时间到期之后, **软件定时器任务**将执行预设的回调函数.
>- 软件定时器的任务的堆栈大小/优先级/命令队列长度, 也需要在配置文件中进行配置.
>
>```C
>(timers.c  237)   
>BaseType_t xTimerCreateTimerTask( void )
>{
>        // ...
>( 310 )
> xReturn = xTaskCreate( prvTimerTask,
>                       configTIMER_SERVICE_TASK_NAME,
>                       configTIMER_TASK_STACK_DEPTH,
>                       NULL,
>                       ( ( UBaseType_t ) configTIMER_TASK_PRIORITY ) | portPRIVILEGE_BIT,
>                       &xTimerTaskHandle );
>            // ...
>}
>
>// 软件定时器
>#define configUSE_TIMERS    1
>// 软件定时器任务的栈深度
>#define configTIMER_TASK_STACK_DEPTH  128
>// 软件定时器任务的优先级
>#define configTIMER_TASK_PRIORITY 3
>// 软件定时器的命令队列长度
>#define configTIMER_QUEUE_LENGTH 4
>```
>
>- 命令队列
>
>```C
>// 在软件定时器的使用流程中, 所有定时器的管理, 以及定时到期之后触发回调函数的执行, 都是"定时器任务"负责管理和维护, 但是定时器的设置和启动, 是由普通用户程序'触发'.
>// 在这种情况下, 普通任务通过xTimerCreate()函数创建定时器之后, 要把定时器通过xTimerStart()函数交给"定时器任务"管理, 或者定时器已经交给"定时器任务"管理了, 准备通过xTimerStop()函数停止定时器, 也就是把定时器从"定时器任务"中移除.
>// 也就是说, 在普通任务和"定时器任务"之间, 需要一个信息交互的渠道, 而这个渠道本质是一个消息队列, 我们称这个消息队列为命令队列
>
>// 定时器任务不主动管理定时器, 它只会按照命令队列中的指令来操作定时器
>// 定时器到期后执行回调函数, 这个执行过程是由定时器任务负责的
>// 定时器的启动和停止是任务触发的, 而实际的执行是定时器任务完成的
>```
>
>- 支持单次触发和周期性触发.
>
>```C
>// 所谓单次触发: 定时器触发一次, 然后自动停止. 不会自动重启. 如果需要重启, 需要手动调用xTimerStart()函数或者xTimerReset()函数
>
>// 所谓周期性触发: 定时器可以循环触发多次, 每次定时器计时到期后, 会自动重新开始计时.不需要手动重启.
>```
>
>- 注意定时器的回调函数  在定时器任务的下文中运行.
>
>```C
>// 注意
>
>// 软件定时器适合:
>// 任务超时检测( 例如:按键长按2s触发事件)
>// 定时任务执行( 例如:定时发送心跳包)
>// 非实时性定时控制 ( 例如:LED闪烁)
>
>// 软件定时器不适用于高精度需求:
>// 需要<1ms精度, 应该要使用硬件定时器
>// 需要用于PWM控制, 应该要使用硬件定时器
>// 等
>```

>`xTimerCreate()`创建定时器
>
>```C
>// FreeRTOS用于创建软件定时器的API, 它不会立即启动定时器, 而是返回一个定时器句柄(Handle)
>TimerHandle_t xTimerCreate(
>        const char *pcTimerName,       // 定时器名称(仅用于调试)
>        TickType_t xTimerPeriodInTicks, // 定时器周期(时钟节拍)
>        UBaseType_t uxAutoReload,      // 是否自动重载(pdTRUE/pdFALSE)
>        void *pvTimerID,               // 用户定义的ID
>        TimerCallbackFunction_t pxCallbackFunction // 回调函数指针
>);
>// 返回值: 定时器句柄
>```
>
>`xTimerCreateStatic()`创建定时器
>
>````C
>// FreeRTOS用于创建软件定时器的静态方式, 它不会立即启动定时器, 而是返回一个定时器句柄(Handle), 并且需要手动提供定时器需要内存空间
>TimerHandle_t xTimerCreateStatic(
>    const char *pcTimerName,         // 定时器名称(仅用于调试)
>    TickType_t xTimerPeriodInTicks,  // 定时器周期(时钟节拍)
>    UBaseType_t uxAutoReload,        // 是否自动重载(pdTRUE/pdFALSE)
>    void *pvTimerID,                 // 用户定义的ID
>    TimerCallbackFunction_t pxCallbackFunction, // 回调函数
>    StaticTimer_t *pxTimerBuffer      // 由用户提供的静态定时器内存
>);
>// 返回值: 定时器句柄
>````
>
>`xTimerStart()`启动定时器 
>
>```c
>// FreeRTOS用于启动软件定时器的函数, 当需要启动软件定时器的时候, 可以调用该函数, 这个函数的本质是将"启动命令"通过消息队列, 发送给"定时器任务".
>// 而当定时器任务被调度之后, 定时器任务读取队列信息, 才真正启动定时器. 
>
>BaseType_t xTimerStart(
>    TimerHandle_t xTimer,  // 目标定时器句柄
>    TickType_t xTicksToWait // 阻塞等待时间(当命令队列满时的阻塞时间: 通常为0)
>);
>// 返回值: pdPASS启动定时器成功.
>```
>
>`xTimerStartFromISR()`启动定时器
>
>```C
>// FreeRTOS用于启动软件定时器函数的中断版本, 当需要启动软件定时器的时候, 可以调用该函数, 这个函数的本质是将"启动命令"通过消息队列, 发送给"定时器任务".
>// 而当定时器任务被调度之后, 定时器任务读取队列信息, 才真正启动定时器. 
>
>BaseType_t xTimerStartFromISR(
>    TimerHandle_t xTimer,            // 目标定时器句柄
>    BaseType_t *pxHigherPriorityTaskWoken // 任务切换指示(pdTRUE:表示等中断结束需要切换任务)
>);
>// 返回值: pdPASS启动定时器成功.
>```
>
>`xTimerStop()`停止定时器 
>
>```c
>// FreeRTOS用于停止定时器的函数, 注意该函数不会立即停止定时器, 而是通过命令队列通知定时器任务执行停止操作
>// 同时, 停止定时器, 只是使其不再触发回调函数, 而不是删除定时器, 只是让定时器停止工作, 被停止的定时器可以使用xTimerStart()函数重新启动.
>
>BaseType_t xTimerStop(
>    TimerHandle_t xTimer,  // 目标定时器句柄
>    TickType_t xTicksToWait // 阻塞等待时间(当命令队列满时的阻塞时间: 通常为0)
>);
>// 返回值: pdPASS成功停止定时器
>```
>
>`xTimerStopFromISR()`停止定时器 
>
>```C
>// FreeRTOS用于停止定时器函数的中断版本, 注意该函数不会立即停止定时器, 而是通过命令队列通知定时器任务执行停止操作
>// 同时, 停止定时器, 只是使其不再触发回调函数, 而不是删除定时器, 只是让定时器停止工作, 被停止的定时器可以使用xTimerStart()函数重新启动.
>
>BaseType_t xTimerStopFromISR(
>    TimerHandle_t xTimer,            // 目标定时器句柄
>    BaseType_t *pxHigherPriorityTaskWoken // 任务切换指示(pdTRUE:表示等中断结束需要切换任务)
>);
>// 返回值: pdPASS成功停止定时器
>```
>
>`xTimerReset()`复位定时器
>
>```c
>// 用于重新启动一个软件定时器，并将其超时时间重新计时(无论它是正在运行还是已经到期)
>// 如果定时器已经运行, 则会重置倒计时, 如果定时器未启动, 则相当于xTimerStart()
>// 不会改变定时器的周期性
>
>BaseType_t xTimerReset(
>    TimerHandle_t xTimer,      // 目标定时器句柄
>    TickType_t xTicksToWait    // 阻塞等待时间(当命令队列满时的阻塞时间: 通常为0)
>);
>// 返回值: pdPASS成功重置定时器
>```
>
>`xTimerChangePeriod()`  修改定时器周期
>
>```c
>// 用于修改一个已创建的软件定时器的周期(即,超时时间).
>// 并且无论定时器是否正在运行, 都会立即重新计时, 并按照新的周期重新倒计时
>
>BaseType_t xTimerChangePeriod(
>    TimerHandle_t xTimer,      // 目标定时器句柄
>    TickType_t xNewPeriod,     // 新的定时周期(时钟节拍)
>    TickType_t xTicksToWait    // 阻塞等待时间
>);
>// 返回值:pdPASS表示成功修改定时器周期
>```
>
>`xTimerDelete()`  删除定时器
>
>```c
>// 用于删除一个已经创建的软件定时器, 并释放其占用的资源
>// 如果定时器正在运行, 调用xTimerDelete()会先停止定时器, 然后删除它
>// 这个删除行为, 不会影响其他定时器, 只会删除指定的定时器
>// 如果使用静态方式创建的定时器, 删除之后内存空间需要使用者手动释放
>
>BaseType_t xTimerDelete(
>    TimerHandle_t xTimer,      // 目标定时器句柄
>    TickType_t xTicksToWait    // 阻塞等待时间（通常设为 0）
>);
>// 返回值: pdPASS表示成功删除定时器
>```

# 2. 内存管理

>在FreeRTOS中提供了五种不同的内存管理方式, 以适应不同的内存管理应用场景.
>
>它们的主要区别在于内存分配和释放的灵活性、是否支持动态释放, 以及碎片管理问题.

> **heap_1.c**
>
>```C
>// 在heap_1.c中, 仅支持分配内存, 不支持释放内存
>// 也就意味着仅支持内存分配函数pvPortMalloc(), 不支持释放内存函数vPortFree
>```
>
>```C
>// 这种方式比较适合一旦创建内存不再需要释放的场景.
>// 适合简单/静态的系统, 在这种系统下不会产生内存碎片
>// 只能通过FreeRTOS的系统重启来回收和重新分配内存
>// 优点是代码简单, 效率高
>```

> **heap_2.c**
>
> ```C
> // heap_2.c, 也被称为首次适配算法, 支持释放内存
> // 在heap_1.c的基础上对vPortFree()释放内存函数进行支持.
> 
> // 所谓首次适配算法(First Fit), 就是在内存的空闲链表中找到第一个满足要求的内存块进行内存分配.
> // 这种查找的本质实际上就是按地址递增遍历空闲链表, 知道找到一个大小可以满足分配空间需求的内存块, 则开始分配内存
> // 如果找到的这个内存块, 大于所需要的分配的内存, 则把这块内存拆分成两部分, 一部分分配给请求的内存, 剩下的部分作为一个新的空内存块存在
> 
> // 上述分配的方法极容易产生内存碎片.因为每次分配时, 不会优先考虑最适合的块, 而是选择最先找到的内存块.
> // 并且在程序的不断内存开辟和释放过程中, 容易产生比较多的小块内存, 这会导致内存不够使用
> // 但是从另一个层面上讲, 这种分配方式查找速度快, 因为找到第一个满足需求的块就立即分配, 不用再继续搜索
> ```

>**heap_3.c**
>
>```C
>// heap_3.c是在heap_2.c的基础上, 对malloc函数和free函数使用提供支持.
>// 但是本质上和heap_2.c没有本质的区别, 甚至由于引入了malloc函数和free函数, 可能极大的增加FreeRTOS的内核代码量
>```

>**heap_4.c**
>
>```C
>// heap_4.c又被称为最佳适配算法
>// heap_4.c是在heap_2.c的基础上, 支持内存的申请和释放, 即pvPortMalloc()函数和vPortFree()函数
>// 但是在heap_4.c中, 如果需要查找和分配一个内存空间, 它不是从地址的向上查找第一个满足情况的内存分片; 而是在空闲内存块链表中, 找到一个最合适的内存块进行分配(即: 大于等于所需内存的最小内存块)
>// 除此之外heap_4.c还支持空闲内存块的合并, 把相邻的空闲内存块合并到一起, 这种对空闲内存合并和整理的行为, 极大的减少内存碎片的产生
>```

>**heap_5.c**
>
>```c
>// heap_5.c是在当前系统有多个独立内存区域的时候, 所适用的一种内存管理办法.
>// 它可以将不同的独立的内存块, 从逻辑上组成一个堆空间, 并在其中进行内存的分配和释放.
>// 但是这种分配方式处理需要手动配置多个堆的区域, 并且并不是适用每一个芯片架构平台
>```

# 3. 低功耗

>理论上的低功耗模式
>
>````C
>// Sleep模式:
>// CPU停止运行, 但保持供电(低功耗) (即:不执行指令、不运行任务, 即:把供给CPU的时钟关闭)(但是供电保证CPU内部寄存器值不丢失)
>// RAM、寄存器、外设保持不变(数据不丢失)
>// 系统时钟可继续运行(如果不手动关闭)
>// 任意中断都可唤醒CPU(如 SysTick、UART、GPIO 等)
>// 适用于快速低功耗切换,功耗比STOP/Standby高, 但恢复快。
>// 外设可以正常运行(外设不依赖于CPU)
>
>// Stop模式:
>// CPU内核停止运行, 主时钟(HCLK)关闭(等价于外设没有时钟供应), 但低功耗时钟(LSI/LSE)可继续运行
>// 关闭时钟不停止供电, RAM、寄存器、外设状态保持不变
>// 外设基本停止(除RTC/UART)
>// 只能通过RTC定时器或外部中断(EXTI、UART、GPIO)唤醒
>// 比Sleep模式功耗更低, 但比Standby模式唤醒更快
>
>// Standby模式:
>// CPU完全断电(寄存器数据丢失), 所有时钟(HCLK、PCLK、Systick)都关闭
>// RAM和寄存器数据丢失，但RTC仍可运行
>// 所有外设关闭, 只有RTC可用
>// 仅能通过RTC唤醒, 不能通过UART等外设唤醒
>// 复位后重新执行main(), 像重新上电一样启动
>````
>
>通常, 要降低运行FreeRTOS的微控制器的功耗, 可使用空闲任务将微控制器置于低功耗状态. 
>
>```c
>// 在FreeRTOS中我们可以通过将configUSE_TICKLESS_IDLE定义为1, 可以启用内置的无滴答空闲功能
>
>// 所谓无嘀嗒空闲功能:
>// 即,当所有任务都处于阻塞状态(基本上都是因为vTaskDelay进入阻塞, 基本不会因为访问互斥资源而导致大家都进入阻塞), 只有空闲在执行的时候, 并且我们又给FreeRTOS配置了低功耗模式.
>// 那么空闲任务就会停止SysTick嘀嗒定时器(关闭SysTick中断触发), 这样SysTick中断就不会产生, 就无法发生任务切换.
>
>// 甚至在某些低功耗模式下, 我们可以给CPU停止运行并断电.
>// 比如在Standby模式(待机模式)下, CPU在停止运行之前会计算多久之后需要要被唤醒(比如1000秒之后,有任务会从vTaskDelay中醒来需要上CPU运行), 那么CPU就会通过控制电源管理单元(PMU), 配置RTC唤醒机制, 要求RTC(实时时钟)设置一个定时器(定时1000秒), 并且CPU会关闭自己的时钟, 而且CPU完全断电(既不切换任务, 也不执行任何程序)
>// 而RTC实时时钟是一个可以独立运行(不依赖于CPU或者别的外设等)的逻辑单元, 并且也可以充当一个闹钟, 当给这个RTC定时器到达指定时间(比如上述说的1000秒), RTC会通知电源管理单元(PMU)恢复CPU供电运行, 并且要求重新触发SysTick中断, 退出低功耗
>
>// 在FreeRTOS退出低功耗之后, 会更新和调整当前系统嘀嗒计时时间, 保证系统整体运行时间正确, 不会因为进入低功耗而丢失时钟节拍计数, 确保任务的时间基准正确.
>```
>
>STM32
>
>```C
>// 需要注意的是在STM32F103C8T6中, MCU仅支持两种低功耗模式:
>// Sleep模式
>// Stop模式
>// 这是因为Standby模式需要备份寄存器和备用电源域等硬件支持
>```
>
>```C
>// 在FreeRTOSConfig.h中, 启用Tickless Idle模式:
>
>#define configUSE_TICKLESS_IDLE    1  // 启用无滴答低功耗模式
>#define configEXPECTED_IDLE_TIME_BEFORE_SLEEP 2  // 任务空闲2个时钟节拍以上才进入低功耗
>
>
>// 在开启上述配置之后, 只要能保证某一时刻:
>//	1, 空闲任务是唯一能够运行的任务, 即其他所有应用程序任务要么处于阻塞状态, 要么处于挂起状态.
>//	2, 下一个需要上CPU的任务至少还有configEXPECTED_IDLE_TIME_BEFORE_SLEEP个时钟节拍
>// 那么FreeRTOS就会控制进入低功耗状态
>
>// 在FreeRTOS中, 进入低功耗状态的底层是由portSUPPRESS_TICKS_AND_SLEEP函数实现的:
>
>(portmacro.h  131 )
>#ifndef portSUPPRESS_TICKS_AND_SLEEP
>extern void vPortSuppressTicksAndSleep( TickType_t xExpectedIdleTime );
>#define portSUPPRESS_TICKS_AND_SLEEP( xExpectedIdleTime )    vPortSuppressTicksAndSleep( xExpectedIdleTime )
>#endif
